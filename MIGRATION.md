# Migration guide

## `v1.x` → `v2.0.0`

These changes can break 1.x code. The [TypeScript migration guide](https://github.com/nuntly/nuntly-sdk-typescript/blob/main/MIGRATION.md) covers the same API changes with TypeScript examples.

### Breaking changes

- `agents().memory().retrieve(...)` no longer throws `NotFoundError` when nothing is saved: it returns an empty `AgentMemory` whose `id()`, `createdAt()` and `updatedAt()` are empty, with an empty `memory()` and an empty `summary()`. `NotFoundError` now means the `inboxId` or `threadId` does not exist in your organization, on `retrieve` and on an `upsert` that would create a memory record. An empty `inboxId` or `threadId` is rejected with `UnprocessableEntityError`. These statuses come from the API, so a 1.x Java client sees them too: a `retrieve` that relied on `NotFoundError` gets an `AgentMemory` with a null `id()` and `createdAt()` although the 1.x type declares them `String`, an `upsert` that would create a memory record with a thread id of your own, not a Nuntly thread, gets `NotFoundError` and saves nothing, and an empty `inboxId` or `threadId` gets `UnprocessableEntityError`.
- `organizations().usage().retrieve(orgId)` returns usage under `email`, typed as nested records instead of the former `transactional` map: `email().daily()` and `email().monthly()` each carry `used()`, `limit()` (`Optional<Long>`, empty when the window is unlimited), `resetsAt()` and a `breakdown()` by channel, for example `email().daily().breakdown().broadcast().sent()`.
- Lists of objects are lists of nested `<Field>Item` records instead of `List<Map<String, Object>>`: `BulkEmailsResponse.emails()` and `CreateBulkEmailsResponse.emails()` (`EmailsItem`), `DomainRecordsResponse.records()` (`RecordsItem`, with `DnsRecordType recordType()` and `DnsRecordGroup group()`), `EmailResponse.attachments()` (`AttachmentsItem`), `EmailsStatsResponse.stats()` (`StatsItem`), `BounceDetail.bouncedRecipients()`, `ComplaintDetail.complainedRecipients()`, `DeliveryDelayDetail.delayedRecipients()`, and the `headers()` of `EmailEvent` and of every email event data record, which all share `EmailEvent.HeadersItem`.
- `list(...)` takes a `<Resource>ListParams` record instead of positional `Optional` arguments: `nuntly.emails().list(Optional.empty(), Optional.of(20))` becomes `nuntly.emails().list(EmailsListParams.builder().limit(20).build())`, and a sub-resource keeps its path argument first (`nuntly.inboxes().threads().list(inboxId, InboxesThreadsListParams.builder().limit(20).build())`). `list()` without arguments is unchanged.
- Optional request fields the API accepts as `null` are `JsonNullable<T>` instead of `Optional<T>`, so `null` can be sent: `UpdateInboxRequest.name`, `UpdateThreadRequest.agentId`, `UpdateNamespaceRequest.externalId` and `AgentMemoryRequest.summary`. Builder code keeps compiling and behaves as before (a `null` passed to the setter still leaves the field out); use the new `clearX()` method to send `null`, for example `UpdateInboxRequest.builder().clearName()`. Code that reads these components or calls the canonical constructor must use `JsonNullable`. A `null` value in agent `memory` and email `variables` (single and bulk), including one in a nested map or list, is now sent instead of dropped; in email `headers`, where the API rejects `null`, it is still dropped.
- The email event records (`EmailEvent` and nine `Email*EventData` records such as `EmailSentEventData`) have a new `Optional<String> broadcastId` component after `bulkId`. Code that reads them through accessors keeps compiling; code that calls their canonical constructor or deconstructs them with record patterns must add the component.
- `disabledReason()` on `WebhookResponse`, `WebhooksResponseItem` and `CreateWebhookResponse` is an `Optional<WebhookDisabledReason>` enum (`MANUAL`, `AUTO_CONSECUTIVE_FAILURES`) instead of a `String`.
- `CreateWebhookRequest.events` and `UpdateWebhookRequest.events` are a `List<WebhookEventType>`, the 14 event types a webhook delivers, instead of a `List<EventType>`. The 7 types that are never delivered by webhook (`EMAIL_QUEUED`, `EMAIL_SCHEDULED`, `EMAIL_PROCESSED`, `EMAIL_SENDING`, `EMAIL_RENDERING_FAILED`, `EMAIL_SUBSCRIBED`, `EMAIL_UNSUBSCRIBED`) have no constant there, and the API answers `UnprocessableEntityError` for them instead of a 500. Webhook responses keep `List<EventType>`: to change the subscription, build the list from the `WebhookEventType` constants you want to receive, or leave `events` out of the update to keep the stored list.
- `WebhookEvent`, the sealed type `Webhook.verify` returns, permits the 14 webhook event records and `UnknownWebhookEvent`. `EmailQueuedEvent`, `EmailScheduledEvent`, `EmailProcessedEvent`, `EmailSendingEvent` and their `EmailScheduledEventData` and `EmailSendingEventData` records are removed: no webhook delivers those events and no SDK call returns them, so remove their `case` from a switch over a verified event. A payload of one of those types, or of a type added later, is returned as `UnknownWebhookEvent`. Keep a `default` or `UnknownWebhookEvent` branch: a webhook only receives the types it subscribes to.
- Response fields the API can return as `null` are `Optional` instead of a bare type, and the content `size` is `Optional<Long>` instead of `long`, so a `null` no longer fails parsing: `AgentMemory` (`id`, `createdAt`, `inboxId`, `threadId`, `summary`), `AttachmentResponse` (`filename`, `contentDisposition`, `contentId`), `EmailContentResponse` (`html`, `text`, `mime`, `subjectTemplate`, `htmlTemplate`, `textTemplate`), `EmailContentItem.size`, `MessageContent` (`text`, `html`, `mime`), `MessageContentItem.size`, `InboxResponse` and `InboxesResponseItem` (`name`, `namespaceId`, `namespaceName`, `agentId`), `MessageResponse` and `MessagesResponseItem` (`inboxId`), `NamespaceDetail`, `NamespaceResponse` and `NamespacesResponseItem` (`externalId`), `ThreadResponse` and `ThreadsResponseItem` (`domainId`, `agentId`), `CreateWebhookResponse`, `WebhookResponse` and `WebhooksResponseItem` (`disabledReason`, `disabledAt`). Read them with `orElse`, `map` or `ifPresent`.
- The retry policy matches TypeScript: a 409 is no longer retried unless the API sends `x-should-retry: true`, and a `POST` or `PATCH` is retried only on a 429, never on a 408, a 5xx or an `IOException`, unless it is one of the methods the API deduplicates by `Idempotency-Key` (among the 1.x methods, `emails().send()`, `emails().bulk().send()`, `messages().reply()`, `messages().forward()`, `inboxes().messages().send()` and `inboxes().create()`); an `Idempotency-Key` header alone no longer makes a request retried. `Retry-After` is now honored on any retried response, not only a 429, and also as an HTTP-date. Jitter now shortens the backoff delay (to between 75% and 100% of it) instead of lengthening it. A `Retry-After` above 60 s is no longer waited on: the error for that response is thrown at once.
- An idempotency key is passed in an `IdempotentRequestOptions`, taken only by the methods whose endpoint deduplicates by key. `RequestOptions` no longer has `idempotencyKey`: replace `RequestOptions.builder().idempotencyKey(key)` with `IdempotentRequestOptions.builder().idempotencyKey(key)` in `emails().send()`, `emails().bulk().send()`, `messages().reply()`, `messages().forward()` and `inboxes().messages().send()`. A key passed to a `NuntlyClient` method such as `post` was never sent in 1.x, so remove it.
- `emails().bulk().list(bulkId)` reads one bulk request, not a page, so it is now `emails().bulk().retrieve(bulkId)`.
- `webhooks().events().deliveries(id, eventId)` is now `webhooks().events().deliveries().list(id, eventId)`, a sub-resource like `emails().bulk()`.
- `CursorPage.nextPage()` on the last page throws `NoSuchElementException` instead of sending the previous request again and returning the same page. Check `hasNextPage()` first, or iterate the page. Iterating a page throws `NuntlyError` when the API returns any cursor already requested in that iteration, before fetching it again. `nextPage()` throws `NuntlyError` when the next cursor is the cursor that page was requested with, or when a `fetchPage` you supplied returns `null`; a `nextPage()` loop over a longer cycle is not detected, as in 1.x.
- A request that exceeds the timeout throws `ConnectionError.TimeoutError` instead of a plain `ConnectionError`, and a thread interrupted during a request or a retry wait throws a plain `ConnectionError` instead of `TimeoutError`.
- `Webhook.verify` rejects a timestamp more than the tolerance (5 minutes by default) in the future, as it already did in the past, with the message `Webhook timestamp outside tolerance window` in both cases.
- A response enum, such as `EmailStatus` or `BounceDetailBounceType`, has an `UNKNOWN` member: a value the API adds after your SDK version reads as `UNKNOWN` instead of `null`, and `fromValue` returns it instead of throwing. An exhaustive `switch` over one of these enums needs a `case UNKNOWN` or a `default`. `UNKNOWN.value()` is `null`, and a response record read with `UNKNOWN` can be serialized again: a field holding it is written as `null`, so it is left out of a request, and a list element holding it is written as a `null` element. A query param holding `UNKNOWN` throws `NuntlyError` before the request is sent. The enums only a request uses (`CreateApiKeyRequestPermission`, `MessageContentQueryFormat`, `UpdateApiKeyRequestStatus`, `WebhookEventType`, `WebhookMutableStatus`) have no `UNKNOWN`.
- The unused `ResponseWithData` record is removed.
- A path id equal to `""`, `.` or `..` throws `NuntlyError` before any request is sent. 1.x sent it as is, so the path pointed to another route: `emails().retrieve("")` sent `GET /emails/`. A `null` path id throws `NuntlyError` too, where 1.x sent `null` as the id.
- The hooks run in the TypeScript order: `onRequest` before every attempt, retries included, `onRetry` before each retry, `onResponse` once on the final response, then `onSuccess` or `onError`. It used to call `onRequest` once per request and `onResponse` on every response, retried ones included; a hook that counts requests or responses now sees one `onRequest` per attempt and one `onResponse` per request.
- A JSON integer in a free-form value, such as a `Map<String, Object>` value of agent `memory()`, email `tags()` or a webhook event payload, or an element of a list inside one, reads as a `Long` instead of a `Double`, with its exact value: `2` reads as `2L`, not `2.0`, and `9007199254740993` no longer rounds to `9007199254740992`. A number with a fraction or an exponent (`0.75`, `1e3`) still reads as a `Double`, and an integer beyond the `long` range reads as a `Double`. Code that casts such a value to `Double` throws `ClassCastException`: read it as a `Number` (`((Number) value).doubleValue()`). `NuntlyClient.defaultGson()` decodes the same way.

### New in 2.0.0 (no change needed)

- Every resource method has an overload that takes a `RequestOptions` last (timeout, maximum retries, headers), as the TypeScript methods take `options`: `nuntly.emails().retrieve(id, RequestOptions.builder().timeout(Duration.ofSeconds(10)).build())`. The eight methods that send an idempotency key take an `IdempotentRequestOptions` there instead.
- The broadcast resources.
- The `inboxId`, `threadId`, `format` (a list of the `MessageContentQueryFormat` enum, sent as `format=html`; an empty list or a `null` element throws `NuntlyError`) and `markRead` (a `Boolean`) query parameters on the agent memory, message content and thread `retrieve` methods, passed in a params record such as `ThreadsRetrieveParams.builder().markRead(true).build()` or `MessagesContentRetrieveParams.builder().format(List.of(MessageContentQueryFormat.HTML)).build()`. The path-only overloads keep compiling.
- An `Idempotency-Key` on broadcast and inbox creation.
- A `builder()` on every record a request body carries, such as `Attachment`, `Tag`, `CreateBulkEmail`, `CreateBulkFallback` and `VariableDeclaration` (`Tag.builder().name("category").value("welcome").build()`).
- `ApiError` has `code()`, `title()` and `details()`, like the TypeScript `APIError`.
- `NuntlyClient.defaultGson()` returns the Gson configuration the client and `Webhook.verify` decode with, to read or write SDK records the same way.
- `NuntlyClient.list(path, itemType, query, opts)` takes a `Map<String, ?>` query instead of a `Map<String, String>`, like `NuntlyClient.get`: an enum goes out as its wire value and a list as repeated keys, on every page. A `Map<String, String>` argument keeps compiling.

### Fixed in 2.0.0

- A 2xx response whose body is empty or not a JSON object, such as a proxy's HTML page, throws a plain `NuntlyError`, passed to `onError` (not `onSuccess`), as in TypeScript. Its message says the request may have been applied: check before you send it again. It used to throw a raw Gson `JsonSyntaxException` or `IllegalStateException`. `rawRequest`, `deleteVoid` and `webhooks().events().replay()` do not read the body.
- A timeout of `Duration.ZERO` sets no timeout, as in TypeScript: in `ClientOptions` neither on the attempts nor on opening a connection, in `RequestOptions` none on the attempts of that call, whose connection still follows the client timeout. A negative one throws `NuntlyError`. Since 1.x both threw `IllegalArgumentException` from the JDK HTTP client.
- `ClientOptions.toString()` shows `apiKey=[redacted]`, and the `HttpRequest` every hook receives, directly or through `response.request()`, `RetryContext.request()` and `ApiError.rawResponse().request()`, carries `Authorization: Bearer [redacted]`. Since 1.x the record's `toString()` and every hook argument carried the API key; the request sent to the API still carries it.
- `Webhook.verify` accepts every signature of the header during a signing secret rotation. Since 1.x it kept only the first one, so `t=<ts>,v0=<sigNew>,<sigOld>` failed verification with the previous secret until the rotation ended.
- An `onError` hook that throws no longer replaces the error of the request: the caller receives the original `ApiError` or `ConnectionError`, with the hook's exception in `getSuppressed()`. The hook's exception used to be thrown instead.
- `Webhook.verify` throws `WebhookVerificationError` with the message `Invalid webhook payload`, the parsing error as its cause, when a correctly signed payload is not a valid event. Since 1.x it threw the raw Gson exception (`JsonSyntaxException`, `IllegalStateException`).
- The client drops the trailing `/`s from `baseUrl` (for example `nuntly.base-url: https://api.nuntly.com/` in Spring). Since 1.x such a base URL sent every request to `//path`.
